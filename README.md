# 课题组Git账号与项目维护管理方案（免费化易管理版）

# 一、方案总则

## 1.1 方案目标

1.  采用免费Git平台，搭建统一、轻量化的账号与项目管理体系，实现学生项目集中管控、版本追溯与高效协作；

2.  简化权限层级与操作流程，降低管理成本，适配课题组高效管控需求，规避越权、代码丢失等风险；

3.  规范核心开发流程（分支、提交、合并），配套基础CLI操作指南，提升代码可维护性，沉淀可复用技术资产；

4.  便于负责人实时监控项目进度、指导老师审查代码，实现“零成本+易管理+快上手”三重目标。

## 1.2 适用范围

课题组全体成员（负责人、指导老师、学生），及所有基于Git管理的项目（含科研代码、实验脚本、文档、数据集描述等）；适用于Windows、Mac、Linux全系统，聚焦命令行（CLI）核心操作，兼顾新手易用性。

## 1.3 核心原则

1.  免费优先：全程采用免费Git平台与工具，无任何额外成本投入；

2.  简化高效：权限与流程极简设计，配套基础CLI操作，降低管理与学习成本，便于快速落地；

3.  统一管控：账号、项目、权限集中配置，避免分散管理导致的混乱；

4.  安全可控：通过免费功能实现备份、权限审计，防范代码泄露与误操作风险。

# 二、Git平台选型（免费优先，易管理为主）

聚焦免费且支持团队管理的平台，全课题组统一使用单一平台，杜绝跨平台分散管理，降低管控难度：

## 2.1 优选免费平台及核心优势

|推荐平台|核心优势（免费功能）|适配亮点|
|---|---|---|
|Gitee（国内首选）|1.  国内访问稳定，无网络延迟问题；2.  免费支持无限私有仓库、5人以内团队（超5人可创建多个免费团队）；3.  自带分支保护、合并请求（MR）、操作日志、仓库备份等核心功能；4.  支持中文界面，学生上手门槛低；5.  与Git CLI无缝适配，命令行操作无兼容问题。|适配课题组内部分享，无外网依赖，团队管理功能直观，便于负责人统筹，新手CLI操作反馈清晰。|

## 2.2 平台统一规范（极简易记）

1.  账号命名：统一采用“姓名拼音首字母+学号后4位”（如张三，学号2023001，账号：zs2001），便于快速识别归属；

2.  密码要求：需包含大小写字母、数字（长度≥8位），定期（每3个月）修改，禁止共用账号，负责人登记账号台账备查；

3.  个人设置：所有成员需绑定课题组统一邮箱（如xxx-lab@xxx.com），开启“登录提醒”，防范账号被盗；首次使用需在CLI中配置用户信息，确保提交记录可追溯。

# 三、账号与权限管理（简化层级，易管控）

## 3.1 账号层级划分（二级极简架构）

简化为“负责人/指导老师（管理员）→ 学生（开发者）”二级架构，减少层级冗余，提升管理效率：

### 3.1.1 一级：管理员（课题组负责人+指导老师）

1.  账号权限：团队/项目管理员权限，可创建/删除项目、添加/移除成员、分配权限、审批合并请求、查看操作日志、配置备份；

2.  分工管控：负责人统筹全局（账号台账、平台配置、CLI操作规范制定），指导老师负责对应项目的成员管理、代码审核，各司其职。

### 3.1.2 二级：学生（开发者）

1.  账号权限：仅获得对应项目的“开发者权限”（可创建功能分支、提交代码、发起合并请求，无删除项目、修改权限等操作）；

2.  核心职责：遵循规范提交代码、编写清晰提交说明、配合审核，禁止直接操作主分支；熟练掌握基础CLI操作，确保日常开发顺畅。

## 3.2 免费平台权限分配细则（以Gitee/GitHub为例）

|操作权限|管理员（负责人/指导老师）|学生（开发者）|管控说明（免费功能实现）|
|---|---|---|---|
|创建/删除项目|√|×|负责人统一创建项目，按研究方向分类（如“药品检测-项目组”），避免项目混乱|
|添加/移除成员|√|×|学生加入项目需由指导老师申请，管理员审核添加，避免无关人员进入|
|创建/提交分支|√（可操作所有分支）|√（仅可操作个人功能分支）|开启“主分支保护”（免费功能），禁止学生直接提交主分支，CLI提交将被平台拒绝|
|发起/审批合并请求|√（审批）|√（发起）|学生可通过CLI发起合并请求，或在平台网页端操作，需@指导老师审批，审核通过方可合并|
|查看操作日志/备份|√|×|管理员可通过日志追溯操作，利用平台免费备份功能定期备份，学生可通过CLI查看本地操作记录|
## 3.3 账号生命周期管理（简化流程，易落地）

### 3.3.1 账号创建

1.  学生提交申请：加入课题组后，向指导老师提交“Git账号申请”（含姓名、学号、研究方向）；

2.  管理员创建账号：指导老师审核后，由负责人统一创建平台账号，分配初始密码（学生首次登录强制修改）；

3.  台账登记：负责人同步更新“课题组Git账号台账”（含账号、姓名、学号、权限、创建时间），便于查询；

4.  初始配置：学生登录平台后，需在本地CLI中配置用户名与邮箱（与平台账号一致），确保提交记录关联正确账号。

### 3.3.2 账号变更与注销

1.  权限变更：学生更换项目时，指导老师直接在平台调整权限，无需负责人审批，简化流程；学生需在CLI中更新远程仓库地址（若项目变更）；

2.  账号注销：学生毕业/退出时，提前1周告知指导老师，确认代码合并、文档归档后，管理员移除其所有项目权限、注销账号，备份其提交的资产；学生需删除本地CLI中的账号配置，避免信息泄露。

# 四、项目管理规范（极简流程，易执行）

## 4.1 项目创建与分类（统一规范，易查找）

### 4.1.1 项目命名规范

统一采用“研究方向-项目名称-指导老师”格式，字母小写，连字符分隔（如：drug-detection-yolov8-zhanglaoshi），快速识别项目归属与核心内容；远程仓库地址与项目名称一致，便于CLI拉取与推送。

### 4.1.2 项目目录结构（极简通用）

1.  分类创建：按研究方向创建项目组，每个项目组下包含对应子项目（如“图像分割项目组”含“医学图像分割”“药品包装分割”子项目）；

2.  目录规范（适配所有语言，易维护）：

```Plain Text

drug-detection-yolov8-zhanglaoshi/
├── docs/          # 文档目录（需求、设计、实验报告、依赖说明）
├── src/           # 核心代码目录（按模块分类，如model、data）
├── scripts/       # 测试/批量处理脚本
├── .gitignore     # 忽略文件（缓存、日志、依赖包等，避免冗余提交）
└── README.md      # 项目说明（功能、使用方法、负责人、CLI操作简要指引）
```

3.  核心要求：禁止根目录存零散文件，所有内容按目录归档，确保结构清晰，新成员可快速上手；.gitignore文件需包含系统缓存（如.DS_Store、__pycache__）、依赖包目录（如venv、node_modules）等，避免无效提交。

## 4.2 分支管理规范（简化版Git Flow，易操作）

采用“主分支+功能分支”双分支模型，移除开发分支，减少分支冗余，降低学生操作难度：

### 4.2.1 分支类型与用途（仅2类，易记）

|分支名称|用途|权限限制|
|---|---|---|
|main/master（主分支）|存放稳定版本（实验达标、论文投稿版），核心代码唯一来源，所有开发完成的功能最终合并至此|开启保护，禁止直接提交，仅可通过合并请求更新，CLI直接推送将被拒绝|
|feature/xxx（功能分支）|学生开发具体功能/修复bug（命名：feature/姓名首字母-功能，如feature/zs-data-preprocess），专注单一任务开发，避免多功能混编|学生可创建、提交，完成后发起合并请求，合并后需删除该分支|
### 4.2.2 分支操作流程（3步极简）

1.  创建分支：学生从主分支（main）创建个人功能分支，专注单一功能开发，避免多功能混编；

2.  提交与合并：开发完成后，学生发起合并请求（MR/PR），@指导老师审核，审核通过后由管理员合并至主分支；

3.  分支清理：合并完成后，学生删除个人功能分支，避免分支冗余，保持仓库整洁；所有流程可通过CLI或平台网页端完成，推荐新手先熟悉CLI操作。

## 4.3 代码提交规范（简单易懂，易执行）

### 4.3.1 提交信息格式（统一3类核心类型）

简化为“类型：描述”格式，避免复杂分类，便于学生记忆与管理员追溯：

1.  类型：feat（新增功能）、fix（修复bug）、docs（文档更新）；

2.  描述：简洁说明内容（≤30字），避免模糊表述，使用中文，便于团队沟通。

示例：feat：新增药品图片预处理函数；fix：修复训练loss计算错误；docs：更新实验记录与CLI操作指引。

### 4.3.2 提交前检查项（3项核心，易落地）

1.  代码可运行：无语法错误、核心功能可正常执行，本地测试通过；

2.  注释清晰：新增函数/核心逻辑添加注释，说明功能与参数，便于他人理解与后续维护；

3.  无冲突：提交前通过CLI拉取主分支最新代码，解决冲突后再提交，避免合并失败。

# 五、Git CLI核心操作指南（必备基础，易上手）

本章节汇总日常开发必备的Git命令行（CLI）操作，按“初始化-日常开发-分支操作-冲突解决-异常处理”分类，配套说明与示例，适配新手快速掌握，所有命令适用于Windows、Mac、Linux系统。

## 5.1 前期准备：Git安装与账号配置

### 5.1.1 Git安装（免费）

1.  下载地址：官网（https://git-scm.com/downloads），根据系统选择对应版本，默认安装即可；

2.  验证安装：打开终端（Windows：cmd/PowerShell，Mac/Linux：Terminal），输入命令 `git --version`，若显示版本号（如git version 2.45.1），则安装成功。

### 5.1.2 账号初始配置（与平台账号一致）

安装完成后，首次使用需配置用户名与邮箱，确保提交记录关联正确账号，命令如下：

```Plain Text

# 配置用户名（与Gitee/GitHub账号一致，如zs2001）
git config --global user.name "你的用户名"
# 配置邮箱（与平台绑定邮箱一致，如xxx-lab@xxx.com）
git config --global user.email "你的邮箱"
# 验证配置是否成功
git config --global --list
```

说明：--global参数表示全局配置，后续所有项目均使用该账号；若需单独配置某个项目，可进入项目目录后去掉--global参数。

## 5.2 核心操作：项目克隆与初始化

### 5.2.1 克隆远程项目（从平台拉取项目到本地）

当需要参与已有项目时，通过克隆命令将远程仓库拉取到本地，命令如下：

```Plain Text

# 克隆远程项目（url为项目远程仓库地址，可从平台复制）
git clone 远程仓库URL
# 示例（Gitee项目）
git clone https://gitee.com/xxx-lab/drug-detection-yolov8-zhanglaoshi.git
```

说明：克隆完成后，本地将自动创建与项目名称一致的文件夹，进入该文件夹即可进行开发；远程仓库地址可在Gitee/GitHub项目页面的“克隆/下载”按钮中获取，选择HTTPS协议（无需配置SSH，新手友好）。

### 5.2.2 本地初始化项目（首次创建项目并推送至平台）

当需要创建新项目时，先在本地初始化，再推送至平台远程仓库，命令如下：

```Plain Text

# 1. 进入本地项目文件夹（先在电脑中创建对应文件夹，如drug-detection-yolov8-zhanglaoshi）
cd 本地项目文件夹路径
# 2. 初始化Git仓库（生成.git隐藏文件夹，用于版本控制）
git init
# 3. 添加所有文件到暂存区（.表示当前目录下所有文件）
git add .
# 4. 提交暂存区文件到本地仓库（按规范填写提交信息）
git commit -m "feat：初始化项目，添加基础目录与文档"
# 5. 关联远程仓库（url为平台创建的空仓库地址）
git remote add origin 远程仓库URL
# 6. 推送本地仓库到远程仓库（首次推送需加-u参数，绑定分支）
git push -u origin main
```

说明：平台需先创建空仓库（无任何文件），再执行上述命令；首次推送时可能需要输入平台账号与密码（或验证码），按提示操作即可。

## 5.3 日常开发：文件提交与远程同步

### 5.3.1 提交文件到本地仓库

开发过程中，定期提交文件到本地仓库，确保代码实时备份，命令如下：

```Plain Text

# 1. 查看文件状态（了解哪些文件被修改、新增、删除）
git status
# 2. 添加指定文件到暂存区（xxx为文件名/目录名，如src/main.py）
git add 文件名/目录名
# 或添加所有文件到暂存区（推荐日常使用，便捷高效）
git add .
# 3. 提交到本地仓库（按规范填写提交信息，不可省略）
git commit -m "类型：描述"
# 示例
git commit -m "fix：修复数据预处理函数的参数错误"
```

说明：git status命令可实时查看文件状态，红色表示未添加到暂存区，绿色表示已添加到暂存区；提交信息需严格按规范填写，便于追溯版本变更。

### 5.3.2 拉取远程仓库最新代码（同步团队更新）

提交代码前，需先拉取远程仓库最新代码，避免冲突，命令如下：

```Plain Text

# 拉取远程main分支的最新代码到本地（默认关联origin远程仓库）
git pull origin main
```

说明：若拉取时提示“fatal: refusing to merge unrelated histories”（无关历史合并），可添加--allow-unrelated-histories参数强制合并，命令：git pull origin main --allow-unrelated-histories。

### 5.3.3 推送本地代码到远程仓库

本地提交完成后，推送至远程仓库，实现团队共享与备份，命令如下：

```Plain Text

# 推送本地main分支到远程main分支
git push origin main
# 若推送功能分支（如feature/zs-data-preprocess）
git push origin feature/zs-data-preprocess
```

说明：若推送功能分支时提示“failed to push some refs”，可能是远程仓库无该分支，直接推送即可（Git将自动在远程创建对应分支）。

## 5.4 分支操作：创建、切换与合并

### 5.4.1 创建与切换分支

从主分支创建功能分支，切换到功能分支进行开发，命令如下：

```Plain Text

# 1. 确保当前在main分支（先切换到main分支）
git checkout main
# 2. 拉取main分支最新代码（避免基于旧版本创建分支）
git pull origin main
# 3. 创建功能分支（如feature/zs-data-preprocess）
git branch feature/zs-data-preprocess
# 4. 切换到功能分支（进入该分支进行开发）
git checkout feature/zs-data-preprocess
# 或创建并切换分支（一步完成，推荐使用）
git checkout -b feature/zs-data-preprocess
```

说明：创建分支时需严格按命名规范命名，便于识别；切换分支前需确保当前分支的修改已提交，避免修改丢失。

### 5.4.2 查看分支列表

查看本地与远程所有分支，了解当前所在分支，命令如下：

```Plain Text

# 查看本地所有分支（*表示当前所在分支）
git branch
# 查看本地与远程所有分支
git branch -a
```

### 5.4.3 合并分支（本地合并，用于功能开发完成后）

功能开发完成后，将功能分支合并到主分支（本地），再推送至远程，命令如下：

```Plain Text

# 1. 切换到main分支
git checkout main
# 2. 拉取main分支最新代码（确保合并基于最新版本）
git pull origin main
# 3. 合并功能分支到main分支（如feature/zs-data-preprocess）
git merge feature/zs-data-preprocess
# 4. 推送合并后的main分支到远程
git push origin main
```

说明：合并前需确保功能分支已完成所有开发与测试；若合并时出现冲突，需先解决冲突（见5.5节），再完成合并。

### 5.4.4 删除分支（功能分支合并后清理）

功能分支合并完成后，删除本地与远程分支，避免冗余，命令如下：

```Plain Text

# 删除本地功能分支（合并完成后）
git branch -d feature/zs-data-preprocess
# 若分支未合并，强制删除（谨慎使用）
git branch -D feature/zs-data-preprocess
# 删除远程功能分支（同步清理远程仓库）
git push origin --delete feature/zs-data-preprocess
```

## 5.5 冲突解决：常见冲突处理方法

当多人修改同一文件的同一部分，或拉取/合并时出现冲突（提示“Automatic merge failed; fix conflicts and then commit the result”），按以下步骤处理：

```Plain Text

# 1. 查看冲突文件（Git会标注冲突位置）
git status
# 2. 打开冲突文件，手动解决冲突
# 冲突文件中会出现类似以下标记：
# <<<<<<< HEAD（当前分支内容）
# 你的修改内容
# =======
# 他人的修改内容
# >>>>>>> feature/xxx（对方分支内容）
# 3. 编辑文件，删除冲突标记，保留正确内容，保存文件
# 4. 解决冲突后，添加文件到暂存区
git add 冲突文件名
# 5. 提交冲突解决结果
git commit -m "fix：解决与feature/xxx分支的冲突，调整xxx文件内容"
# 6. 推送至远程仓库
git push origin main
```

说明：冲突解决需与相关开发者沟通，确保保留正确内容；避免随意删除他人修改，解决完成后需测试代码是否可正常运行。

## 5.6 异常处理：常见问题与解决方法

### 5.6.1 提交错误，撤销本地提交

若提交后发现错误（未推送至远程），可撤销最近一次提交，保留修改内容，命令如下：

```Plain Text

# 撤销最近一次提交，修改内容保留在工作区
git reset --soft HEAD~1
# 撤销最近一次提交，修改内容也删除（谨慎使用）
git reset --hard HEAD~1
```

说明：--soft参数仅撤销提交，保留修改内容，可重新修改后提交；--hard参数将删除修改内容，需确认无重要内容后使用。

### 5.6.2 误删文件，恢复文件

若误删本地文件，可通过Git恢复（前提是该文件已提交过），命令如下：

```Plain Text

# 恢复误删的文件（xxx为文件名）
git checkout -- 文件名
# 恢复所有误删的文件
git checkout -- .
```

### 5.6.3 推送失败，提示“authentication failed”

原因：账号密码错误或验证码未通过，解决方法：

1.  重新输入账号密码：推送时按提示输入正确的平台账号与密码；

2.  验证码验证：部分平台（如Gitee）首次推送需验证手机验证码，按提示输入即可；

3.  清除缓存的账号密码（Windows）：控制面板→用户账户→凭据管理器→删除对应Git平台的凭据，重新推送时输入正确信息。
